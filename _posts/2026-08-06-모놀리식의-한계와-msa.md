1부에서는 모놀리식 애플리케이션과 계층형 구조를 살펴봤다. 모놀리스는 개발과 테스트, 트랜잭션 관리가 단순하다는 장점이 있지만 시스템과 조직이 커질수록 모듈의 경계가 흐려지기 쉽다.

MSA(Microservice Architecture)는 이 문제를 해결하기 위해 갑자기 등장한 기술이 아니다. 객체지향의 모듈화, 도메인 중심의 경계, 분산 시스템, 가상화와 클라우드 운영 기술이 오랜 시간 쌓인 결과다.

## 1. 객체지향: 변경을 객체 안에 가두기

절차적 프로그램에서는 데이터와 그 데이터를 처리하는 함수가 떨어져 있는 경우가 많다. 객체지향 프로그래밍(OOP)은 관련된 상태와 행위를 객체에 묶고, 내부 구현을 감추어 변경의 영향을 줄이려 한다.

```java
class Order {
    private OrderStatus status;

    public void cancel() {
        if (status == OrderStatus.SHIPPED) {
            throw new IllegalStateException("배송된 주문은 취소할 수 없습니다.");
        }
        status = OrderStatus.CANCELED;
    }
}
```

주문 취소 규칙이 `Order` 안에 있으므로 다른 코드가 상태를 임의로 바꾸기 어렵다. 이를 캡슐화라고 한다.

객체지향 설계에는 흔히 SOLID 원칙이 사용된다.

| 원칙 | 핵심 질문 |
| --- | --- |
| SRP, 단일 책임 | 이 클래스가 변경되는 이유는 하나인가? |
| OCP, 개방-폐쇄 | 기존 코드를 크게 고치지 않고 기능을 확장할 수 있는가? |
| LSP, 리스코프 치환 | 하위 타입을 상위 타입 대신 사용해도 계약이 유지되는가? |
| ISP, 인터페이스 분리 | 사용하지 않는 기능에 의존하도록 강요받지 않는가? |
| DIP, 의존성 역전 | 핵심 정책이 구체적인 기술에 직접 의존하지 않는가? |

예를 들어 결제 정책이 특정 카드사 API에 직접 의존하지 않고 `PaymentGateway` 인터페이스에 의존하면 구현을 교체하기 쉬워진다.

```java
interface PaymentGateway {
    PaymentResult pay(Money amount);
}

class OrderService {
    private final PaymentGateway paymentGateway;

    OrderService(PaymentGateway paymentGateway) {
        this.paymentGateway = paymentGateway;
    }
}
```

Strategy, Factory, Observer 같은 디자인 패턴은 반복되는 설계 문제에 이름을 붙이고 해결 방법을 공유할 수 있게 했다. 그러나 객체와 패턴만으로는 수백 개의 클래스가 어떤 업무 영역에 속하는지 설명하기 어려웠다. 더 큰 경계를 다루는 방법이 필요했다.

## 2. 모놀리스는 언제 어려워지는가

초기 쇼핑몰 애플리케이션 안에 회원, 상품, 주문, 결제 모듈이 있다고 가정해 보자. 기능이 늘면서 다음과 같은 코드가 생길 수 있다.

```text
OrderService → MemberRepository
OrderService → ProductRepository
OrderService → PaymentRepository
MemberService → OrderRepository
PaymentService → ProductRepository
```

서로의 테이블과 내부 클래스를 직접 참조하면 모듈 사이에 순환 의존성이 생기고, 한 기능을 수정할 때 영향 범위를 예측하기 어려워진다. 데이터베이스도 공유하므로 어느 모듈이 어떤 테이블을 변경할 수 있는지 불분명해진다.

팀 규모가 커지면 기술 문제는 조직 문제와 결합한다. 여러 팀이 하나의 저장소와 배포 일정을 공유하고, 작은 변경도 전체 회귀 테스트를 거쳐야 한다. 특정 기능에 트래픽이 몰려도 전체 애플리케이션을 함께 확장해야 한다.

하지만 이 문제는 먼저 패키지 경계, 접근 제한, 모듈별 테스트로 개선할 수 있다. 곧바로 서비스를 분리하면 기존 코드의 결합이 네트워크 위로 옮겨갈 뿐이다.

## 3. DDD: 업무의 언어로 경계를 찾기

에릭 에반스가 2003년에 소개한 도메인 주도 설계(DDD, Domain-Driven Design)는 복잡한 업무 규칙을 소프트웨어 모델에 충실히 반영하는 접근법이다. DDD는 단순히 Entity나 Repository 클래스를 만드는 방식이 아니다. 개발자와 도메인 전문가가 같은 언어로 문제를 이해하고, 모델이 유효한 경계를 찾는 과정이 핵심이다.

### Domain과 Ubiquitous Language

Domain은 소프트웨어가 해결하려는 업무 영역이다. 쇼핑몰이라면 주문, 결제, 배송, 재고 등이 도메인에 포함된다. 이때 기획자, 개발자, 운영자가 같은 용어를 일관되게 사용하는 것을 보편 언어(Ubiquitous Language)라고 한다.

예를 들어 “주문 완료”가 결제까지 끝난 상태인지, 주문 정보만 접수된 상태인지 합의하지 않으면 같은 단어가 코드마다 다르게 구현된다.

### Entity, Value Object, Aggregate

- Entity는 속성이 바뀌어도 식별자로 구분되는 객체다. 예: `Order(id=100)`.
- Value Object는 식별자보다 값 자체가 중요하며 보통 불변으로 만든다. 예: `Money(10_000, KRW)`.
- Aggregate는 일관성을 함께 지켜야 하는 객체 묶음이다.
- Aggregate Root는 외부에서 Aggregate에 접근하는 유일한 진입점이다.

```java
class Order {                       // Aggregate Root
    private final OrderId id;
    private final List<OrderLine> lines;

    public void changeQuantity(ProductId productId, int quantity) {
        if (quantity < 1) throw new IllegalArgumentException();
        findLine(productId).changeQuantity(quantity);
        recalculateTotalPrice();
    }
}
```

외부 코드가 `OrderLine`을 직접 수정하지 않고 `Order`를 거치게 하면 주문 전체의 불변 조건을 한곳에서 지킬 수 있다. 일반적으로 하나의 트랜잭션에서는 하나의 Aggregate만 변경하도록 설계하면 경계가 명확해진다.

### Bounded Context

같은 단어도 업무 맥락에 따라 의미와 데이터가 다르다. 상품 카탈로그에서 `Product`는 이름, 설명, 이미지가 중요하지만 재고 맥락에서는 SKU와 남은 수량이 중요하다. 두 모델을 하나로 합치면 거대한 공용 모델이 된다.

Bounded Context는 특정 모델과 언어가 일관된 의미를 갖는 명시적인 경계다.

```text
Catalog Context             Inventory Context
Product                     StockItem
- name                      - sku
- description               - availableQuantity
- images                    - warehouseId
```

Bounded Context는 마이크로서비스 경계를 찾을 때 유용한 후보가 되지만 둘이 항상 일대일로 대응하는 것은 아니다. 하나의 Context를 여러 서비스가 구현할 수도 있고, 작은 시스템에서는 여러 Context를 하나의 배포 단위에 둘 수도 있다.

## 4. SOA: 기업 시스템을 서비스로 연결하기

1990년대 말과 2000년대에는 기업마다 서로 다른 언어와 플랫폼으로 만든 시스템을 연결해야 했다. 서비스 지향 아키텍처(SOA, Service-Oriented Architecture)는 재사용 가능한 비즈니스 기능을 서비스로 제공하고 표준 계약을 통해 통신하는 방식을 확산시켰다.

당시에는 XML 기반 SOAP 메시지와 WSDL 인터페이스 정의가 널리 사용됐다. 여러 시스템의 메시지 변환, 라우팅, 보안 정책을 중앙에서 처리하기 위해 ESB(Enterprise Service Bus)를 두기도 했다.

```text
주문 시스템 ─┐
재고 시스템 ─┼─→ ESB → 메시지 변환·라우팅 → 대상 시스템
회계 시스템 ─┘
```

SOA는 이기종 시스템 통합과 서비스 계약이라는 중요한 기반을 만들었다. 그러나 중앙 ESB에 많은 로직이 모이면 변경과 장애의 병목이 되고, 무거운 표준과 조직 간 조율 때문에 독립적인 배포 속도가 떨어질 수 있었다.

MSA는 서비스 분리라는 생각을 이어받으면서도, 작은 자율 팀이 서비스와 데이터를 소유하고 가벼운 HTTP API나 메시징으로 통신하는 방향을 강조했다.

## 5. 클라우드와 컨테이너가 바꾼 운영 방식

서비스를 여러 개로 나누면 배포하고 운영해야 할 단위도 늘어난다. 물리 서버마다 서비스를 설치하던 환경에서는 이 비용이 너무 컸다. 가상화와 클라우드는 필요한 서버를 빠르게 만들고 제거할 수 있게 했으며, 컨테이너는 애플리케이션과 실행 환경을 일관된 단위로 묶었다.

```dockerfile
FROM eclipse-temurin:21-jre
COPY build/libs/order-service.jar app.jar
ENTRYPOINT ["java", "-jar", "/app.jar"]
```

Docker 이미지는 애플리케이션 실행에 필요한 파일과 설정을 패키징한다. 같은 이미지를 개발, 테스트, 운영 환경에서 실행할 수 있으므로 “내 컴퓨터에서는 된다”는 차이를 줄인다.

컨테이너가 많아지자 배치, 복구, 확장, 네트워크 연결을 자동화하는 오케스트레이션 도구가 필요해졌다. Kubernetes 같은 플랫폼과 CI/CD, 중앙 로그, 분산 추적 기술은 수많은 서비스를 운영할 수 있는 기반이 됐다.

## 6. Microservice Architecture

MSA는 애플리케이션을 비즈니스 능력 중심의 작은 서비스로 나누고, 각 서비스를 독립적으로 개발·배포·확장하는 구조다. 일반적인 특징은 다음과 같다.

- 서비스가 명확한 업무 책임을 가진다.
- 서비스별로 독립 배포할 수 있다.
- 각 서비스가 자신의 데이터를 소유한다.
- API나 비동기 메시지로 통신한다.
- 팀이 개발부터 운영까지 서비스 수명 주기를 책임진다.

```text
                 ┌─→ 주문 서비스 ─→ 주문 DB
Client → Gateway ├─→ 상품 서비스 ─→ 상품 DB
                 └─→ 결제 서비스 ─→ 결제 DB
                         │
                         └─→ Message Broker → 알림 서비스
```

### 동기 통신 구현

상품 서비스가 재고 서비스에 즉시 결과를 요청한다면 HTTP나 gRPC를 사용할 수 있다.

```http
POST /stocks/reservations
Content-Type: application/json

{
  "orderId": "order-100",
  "sku": "BOOK-01",
  "quantity": 2
}
```

동기 통신은 흐름을 이해하기 쉽지만 호출 대상이 느리거나 중단되면 요청 전체가 영향을 받는다. timeout, 제한된 retry, circuit breaker를 함께 설계해야 한다. 재시도 때문에 같은 요청이 여러 번 전달될 수 있으므로 멱등성 키도 필요하다.

### 비동기 통신 구현

주문 생성 후 알림처럼 즉시 응답할 필요가 없는 작업은 이벤트로 전달할 수 있다.

```json
{
  "eventId": "evt-20260806-001",
  "eventType": "OrderCreated",
  "occurredAt": "2026-08-06T10:00:00Z",
  "orderId": "order-100",
  "customerId": "customer-7"
}
```

생산자는 메시지 브로커에 이벤트를 발행하고 소비자는 자신의 속도에 맞춰 처리한다. 서비스 간 결합과 순간적인 트래픽을 줄일 수 있지만 중복 처리, 순서, 유실, 최종적 일관성을 고려해야 한다.

## 7. MSA의 장점과 비용

| 장점 | 그에 따르는 비용 |
| --- | --- |
| 서비스별 독립 배포 | 배포 파이프라인과 버전 호환성 관리 필요 |
| 기능별 독립 확장 | 컨테이너·네트워크·관측 인프라 필요 |
| 장애 범위 격리 | timeout과 장애 전파 방지 설계 필요 |
| 팀의 자율성 | 서비스 경계와 소유권 합의 필요 |
| 기술 선택의 유연성 | 기술 종류가 늘면 운영 부담 증가 |

단일 데이터베이스 트랜잭션으로 끝나던 작업도 서비스가 분리되면 분산 트랜잭션 문제가 된다. 로그가 여러 프로세스에 흩어져 장애 원인을 찾기도 어렵다. 네트워크는 함수 호출과 달리 지연되거나 실패하며, 응답이 오지 않았다고 작업이 실행되지 않은 것도 아니다.

따라서 MSA의 본질은 서비스를 작게 만드는 데 있지 않다. **독립적으로 변경할 필요가 있는 업무 경계를 찾고, 분산 시스템의 비용을 감당하면서 팀의 자율성을 확보하는 것**에 있다.

## 마무리

객체지향은 클래스 수준에서 변경을 분리했고, DDD는 도메인 모델과 Bounded Context로 더 큰 업무 경계를 제시했다. SOA는 서비스 계약과 시스템 통합의 기반을 만들었고, 클라우드와 컨테이너는 많은 배포 단위를 운영할 현실적인 수단을 제공했다. MSA는 이 흐름 위에서 등장했다.

다음 글에서는 서비스 내부의 의존성을 다루는 Clean·Hexagonal Architecture, 읽기와 쓰기를 분리하는 CQRS, 서비스 간 일관성을 다루는 Event Driven Architecture와 Saga를 살펴본다. 이어서 Docker, Kubernetes, CI/CD가 아키텍처를 실제 운영 환경에서 어떻게 지탱하는지도 알아본다.
