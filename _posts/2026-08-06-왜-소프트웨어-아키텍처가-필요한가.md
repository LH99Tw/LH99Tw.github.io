프로그램이 작을 때는 기능을 구현하는 것만으로도 충분해 보인다. 하지만 코드가 수만 줄로 늘고, 여러 개발자가 동시에 작업하고, 장애가 실제 사용자에게 영향을 주기 시작하면 이야기가 달라진다. 이제 중요한 질문은 단순히 **“이 기능이 동작하는가?”**가 아니다.

- 새로운 기능을 기존 코드와 충돌하지 않게 추가할 수 있는가?
- 사용자가 늘어났을 때 일부 기능만 확장할 수 있는가?
- 데이터베이스나 외부 API에 장애가 생겼을 때 어디까지 영향을 받는가?
- 팀원이 코드의 위치와 의존 관계를 빠르게 이해할 수 있는가?

소프트웨어 아키텍처는 이런 질문에 답하기 위해 시스템의 큰 구조와 구성 요소 사이의 관계를 결정하는 일이다.

## 1. 아키텍처는 무엇을 결정하는가

건축 설계가 방의 위치, 이동 경로, 배관과 전기 설비의 관계를 정하듯 소프트웨어 아키텍처는 다음과 같은 결정을 다룬다.

1. 시스템을 어떤 모듈과 계층으로 나눌 것인가?
2. 각 구성 요소는 어떤 책임을 가질 것인가?
3. 구성 요소끼리 어떤 방식으로 통신할 것인가?
4. 데이터는 어디에 저장하고 누가 변경할 수 있는가?
5. 장애, 보안, 성능, 배포 같은 요구를 어떻게 만족할 것인가?

여기서 기능 요구사항과 품질 속성을 구분할 필요가 있다.

| 구분 | 질문 | 예시 |
| --- | --- | --- |
| 기능 요구사항 | 시스템이 무엇을 해야 하는가? | 주문 생성, 결제, 상품 검색 |
| 품질 속성 | 시스템이 얼마나 잘 동작해야 하는가? | 응답 시간, 가용성, 보안, 변경 용이성 |

같은 주문 기능도 하루 10건을 처리하는 학과 프로젝트와 초당 수천 건을 처리하는 서비스에서는 전혀 다른 구조가 필요하다. 아키텍처는 기능뿐 아니라 **변경과 운영에 드는 비용**까지 결정한다.

## 2. 소프트웨어 아키텍처는 왜 필요해졌을까

초기의 프로그램은 한 사람이 작성하고 한 컴퓨터에서 실행하는 경우가 많았다. 프로그램의 규모가 작았기 때문에 코드와 데이터의 흐름을 한 사람이 모두 파악할 수 있었다. 그러나 1960년대 후반 소프트웨어의 규모와 복잡도가 급격히 증가하면서 일정 지연, 비용 초과, 낮은 신뢰성이 반복되었다. 이를 흔히 **소프트웨어 위기(Software Crisis)**라고 부른다.

이 문제를 해결하기 위해 구조적 프로그래밍, 모듈화, 정보 은닉 같은 아이디어가 발전했다.

- 구조적 프로그래밍은 복잡한 제어 흐름을 순차·선택·반복 구조로 정리했다.
- 모듈화는 큰 프로그램을 작은 단위로 나누었다.
- 정보 은닉은 모듈의 내부 구현을 감추고 필요한 인터페이스만 공개했다.
- 객체지향은 데이터와 행위를 객체라는 단위로 묶어 변화의 범위를 제한하려 했다.

1990년대에 들어 분산 시스템과 대규모 기업용 소프트웨어가 보편화되면서 개별 클래스보다 더 큰 단위의 설계가 중요해졌다. 이때 소프트웨어 아키텍처가 독립적인 연구와 실무 영역으로 자리 잡았다. 이후 인터넷, 클라우드, 모바일 환경을 거치며 아키텍처는 코드 구조뿐 아니라 배포와 운영까지 포함하는 개념으로 확장됐다.

## 3. 관심사의 분리와 의존성

아키텍처를 이해하는 핵심은 **관심사의 분리(Separation of Concerns)**다. 주문 시스템을 예로 들면 다음 책임을 구분할 수 있다.

- HTTP 요청을 해석하고 응답하는 일
- 주문 금액과 할인 정책을 계산하는 일
- 주문 데이터를 저장하는 일
- 결제 시스템이나 메시지 브로커와 통신하는 일

이 책임을 한 함수에 모두 넣으면 처음에는 빠르게 개발할 수 있지만, 결제 수단이나 저장 방식 하나를 바꿀 때 전체 코드를 수정해야 한다. 반대로 책임을 적절히 분리하면 한 부분의 변경이 다른 부분으로 퍼지는 것을 줄일 수 있다.

```java
// 여러 관심사가 한곳에 섞인 예
public void createOrder(HttpRequest request) {
    Order order = parseJson(request.body());
    order.applyDiscount();
    database.execute("INSERT INTO orders ...");
    paymentApi.charge(order.getTotalPrice());
    emailApi.send(order.getCustomerEmail());
}
```

다만 파일이나 클래스를 많이 나눈다고 좋은 아키텍처가 되는 것은 아니다. 중요한 것은 **응집도는 높이고 결합도는 낮추는 것**이다.

- 높은 응집도: 서로 관련된 데이터와 동작이 한 모듈에 모여 있다.
- 낮은 결합도: 한 모듈의 변경이 다른 모듈에 미치는 영향이 작다.

## 4. 모놀리식 아키텍처

모놀리식 아키텍처(Monolithic Architecture)는 시스템의 여러 기능을 하나의 애플리케이션으로 개발하고 배포하는 구조다. 회원, 상품, 주문 기능이 서로 다른 패키지에 있더라도 하나의 실행 파일과 프로세스로 배포된다면 모놀리스라고 볼 수 있다.

```text
사용자
  │ HTTP
  ▼
┌─────────────────────────────┐
│ 하나의 애플리케이션          │
│  ├─ 회원 모듈               │
│  ├─ 상품 모듈               │
│  └─ 주문 모듈               │
└──────────────┬──────────────┘
               │ SQL
               ▼
          ┌──────────┐
          │ Database │
          └──────────┘
```

모놀리스는 낡거나 잘못된 구조가 아니다. 함수 호출만으로 모듈이 통신하므로 네트워크 오류를 신경 쓸 필요가 적고, 하나의 트랜잭션으로 데이터 일관성을 보장하기 쉽다. 로컬 환경에서 전체 시스템을 실행하고 테스트하기도 편하다.

반면 시스템이 커지고 모듈 경계가 무너지면 다음 문제가 생긴다.

- 작은 수정에도 전체 애플리케이션을 다시 빌드하고 배포해야 한다.
- 한 기능의 메모리 누수나 과부하가 전체 프로세스에 영향을 줄 수 있다.
- 여러 팀이 같은 코드와 데이터베이스를 수정하며 충돌한다.
- 특정 기능만 확장하고 싶어도 애플리케이션 전체를 복제해야 한다.

중요한 것은 **모놀리스 자체가 아니라 경계 없는 모놀리스가 문제**라는 점이다.

## 5. 계층형 아키텍처

모놀리식 애플리케이션 내부를 정리하는 대표적인 방법이 계층형 아키텍처(Layered Architecture)다. 일반적으로 다음과 같이 나눈다.

| 계층 | 역할 | 대표 코드 |
| --- | --- | --- |
| Presentation | 입력 검증, HTTP 요청·응답 변환 | Controller |
| Business | 정책과 유스케이스 실행 | Service |
| Persistence | 데이터 조회와 저장 | Repository |
| Database | 영구 데이터 보관 | RDBMS |

주문 생성 요청은 다음 순서로 처리된다.

```text
POST /orders
  → OrderController
  → OrderService
  → OrderRepository
  → Database
```

간단한 구현은 다음과 같다.

```java
@RestController
class OrderController {
    private final OrderService orderService;

    @PostMapping("/orders")
    OrderResponse create(@RequestBody OrderRequest request) {
        return OrderResponse.from(orderService.create(request.toCommand()));
    }
}

@Service
class OrderService {
    private final OrderRepository orderRepository;

    @Transactional
    public Order create(CreateOrderCommand command) {
        Order order = Order.create(command.customerId(), command.items());
        return orderRepository.save(order);
    }
}
```

Controller는 HTTP를, Service는 주문 생성 규칙을, Repository는 저장 기술을 담당한다. 이 구조를 지키면 웹 프레임워크나 데이터베이스 관련 코드가 비즈니스 규칙과 뒤섞이는 것을 줄일 수 있다.

하지만 실제 프로젝트에서는 Service가 모든 로직을 떠안고, 도메인 객체는 getter와 setter만 가진 채, 모든 계층이 데이터베이스 테이블 구조에 종속되기도 한다. 계층을 나누는 목적은 디렉터리 정리가 아니라 **변경 이유가 다른 코드를 분리하는 것**임을 기억해야 한다.

## 6. 3-Tier와 3-Layer는 어떻게 다른가

Layer와 Tier는 자주 혼용되지만 관점이 다르다.

- Layer는 코드의 논리적인 책임 분리다.
- Tier는 실행되는 물리적인 환경이나 프로세스의 분리다.

예를 들어 Controller, Service, Repository가 한 서버 프로세스에 들어 있다면 3개의 Layer이지만 애플리케이션 관점에서는 하나의 Tier일 수 있다. 반면 전형적인 3-Tier 구조는 다음처럼 실행 환경을 나눈다.

```text
Presentation Tier      Application Tier       Data Tier
브라우저·웹 서버   →    비즈니스 서버      →    DB 서버
```

각 Tier를 분리하면 웹 서버와 애플리케이션 서버를 독립적으로 확장하거나 데이터베이스를 별도 네트워크에서 보호할 수 있다. 대신 네트워크 통신, 배포, 장애 지점이 늘어난다.

## 7. 좋은 아키텍처에는 정답이 없다

좋은 아키텍처는 가장 많은 기술을 사용한 구조가 아니라 현재 문제와 제약에 맞는 구조다. 다음과 같은 선택에는 항상 대가가 따른다.

- 성능을 위해 캐시를 넣으면 데이터 동기화 문제가 생긴다.
- 서비스별 독립 배포를 위해 분리하면 네트워크와 데이터 일관성 문제가 생긴다.
- 추상화 계층을 늘리면 변경에는 유연해지지만 처음 읽기는 어려워진다.

따라서 아키텍처 결정은 “유행하는가?”보다 다음 질문에서 시작해야 한다.

1. 지금 가장 중요한 품질 속성은 무엇인가?
2. 실제로 자주 바뀌는 부분은 어디인가?
3. 팀이 운영할 수 있는 복잡도의 한계는 어디까지인가?
4. 이 결정을 나중에 되돌리는 비용은 얼마인가?

## 마무리

소프트웨어 아키텍처는 시스템을 보기 좋게 나누는 그림이 아니라, 기능·변경·운영 과정에서 발생할 비용을 미리 조절하는 설계 활동이다. 모놀리스와 계층형 구조는 여전히 많은 시스템에서 합리적인 출발점이다. 다만 규모가 커질수록 단순한 계층 분리만으로는 팀과 도메인의 경계를 유지하기 어려워진다.
