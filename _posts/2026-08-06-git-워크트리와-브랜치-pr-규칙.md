혼자 개발할 때는 `main` 브랜치에서 바로 커밋해도 큰 문제가 없을 수 있다. 하지만 여러 사람이 같은 저장소를 수정하면 상황이 달라진다. 한 명은 로그인 기능을 만들고, 다른 사람은 결제 버그를 고치며, 운영 서버에는 검증된 코드만 배포해야 한다.

Git은 이런 변경을 분리하고 다시 합칠 수 있게 해준다. 그런데 Git을 처음 배우면 워크트리, 브랜치, `HEAD`, Pull Request가 각각 무엇이며 서로 어떻게 연결되는지 혼동하기 쉽다.

이 글에서는 다음 질문에 답한다.

- 내가 수정한 파일은 Git의 어느 단계에 있는가?
- 브랜치를 바꾸면 파일 내용도 바뀌는 이유는 무엇인가?
- `git worktree`는 일반적인 작업 디렉터리와 무엇이 다른가?
- 협업할 때 브랜치와 Pull Request 규칙은 어떻게 정하는가?
- 충돌과 리뷰 비용을 줄이려면 어떤 습관이 필요한가?

## 1. Git은 왜 만들어졌을까

버전 관리 시스템은 파일의 변경 이력을 저장하고, 특정 시점으로 돌아가거나 여러 사람의 변경을 합치기 위해 사용한다. 과거에는 중앙 서버에 이력을 저장하는 CVS나 Subversion 같은 중앙 집중형 버전 관리 시스템이 널리 쓰였다.

Git은 2005년 리눅스 커널 개발을 위해 만들어진 분산 버전 관리 시스템이다. 각 개발자의 로컬 저장소가 전체 커밋 이력을 가지므로 네트워크가 없어도 커밋, 브랜치 생성, 이력 조회가 가능하다.

GitHub, GitLab 같은 서비스는 Git 저장소를 온라인에서 공유하고 Pull Request, 코드 리뷰, 이슈, CI 같은 협업 기능을 제공한다. 즉, **Git은 버전 관리 도구이고 GitHub의 Pull Request는 그 위에 만들어진 협업 기능**이다.

## 2. Git 저장소의 네 가지 영역

Git의 동작을 이해하려면 파일이 이동하는 네 영역을 구분해야 한다.

```text
Working Tree      Staging Area      Local Repository      Remote Repository
작업 디렉터리  →     인덱스      →     로컬 커밋       →      GitHub
              git add          git commit             git push
```

### Working Tree

Working Tree는 현재 직접 열고 수정하는 파일이 있는 작업 디렉터리다. 아직 저장소 이력에 기록되지 않은 변경도 포함한다.

```bash
git status
```

`git status`는 현재 브랜치와 수정·추가·삭제된 파일, 스테이징 여부를 보여준다. 작업 전후에 가장 자주 확인해야 하는 명령어다.

### Staging Area

Staging Area 또는 Index는 **다음 커밋에 포함할 변경을 고르는 공간**이다.

```bash
git add src/login.ts
git diff --staged
```

파일을 수정했다고 자동으로 커밋에 들어가는 것은 아니다. `git add`로 선택한 변경만 다음 커밋에 포함된다. 관련 없는 수정이 섞여 있을 때 `git add .`보다 파일 경로나 `git add -p`로 범위를 선택하는 편이 안전하다.

### Local Repository

커밋은 선택한 변경과 부모 커밋, 작성자, 메시지 등을 저장한 하나의 스냅샷이다.

```bash
git commit -m "로그인 실패 횟수 제한 추가"
```

커밋은 단순한 저장 버튼이 아니다. 팀원이 변경의 목적을 이해하고 필요할 때 되돌릴 수 있는 논리적인 작업 단위여야 한다.

### Remote Repository

로컬 커밋은 `git push` 전까지 내 컴퓨터에만 존재한다. 원격 저장소에 올려야 다른 팀원이 보거나 Pull Request를 만들 수 있다.

```bash
git push -u origin feature/login-limit
```

여기서 `origin`은 원격 저장소의 관례적인 별칭이고, `feature/login-limit`은 푸시할 브랜치 이름이다.

## 3. 브랜치는 코드 복사본이 아니라 커밋을 가리키는 포인터다

브랜치를 프로젝트 폴더 전체의 복사본으로 이해하기 쉽지만, Git 내부에서 브랜치는 특정 커밋을 가리키는 가벼운 참조다.

```text
A ── B ── C  main
         \
          D ── E  feature/login
```

`feature/login`은 C에서 시작해 D와 E 커밋으로 이동했다. 그동안 `main`은 여전히 C를 가리킨다. 기능이 검증되면 두 이력을 merge하거나 rebase한 뒤 `main`에 반영한다.

### HEAD는 현재 위치를 나타낸다

`HEAD`는 현재 체크아웃한 브랜치를 가리킨다.

```text
HEAD → feature/login → commit E
```

새 커밋을 만들면 현재 브랜치 포인터와 `HEAD`가 새 커밋으로 이동한다. 브랜치를 전환할 때 Working Tree의 파일이 달라지는 이유는 Git이 해당 브랜치가 가리키는 커밋에 맞춰 파일을 다시 배치하기 때문이다.

### 기능 브랜치 만들기

작업 전에는 원격의 최신 이력을 받고 새 브랜치를 만든다.

```bash
git switch main
git pull --ff-only origin main
git switch -c feature/login-limit
```

`--ff-only`는 로컬과 원격 이력이 갈라졌을 때 Git이 예상하지 않은 merge commit을 자동으로 만들지 않게 한다.

브랜치 이름은 팀이 한눈에 목적을 알 수 있도록 정한다.

```text
feature/login-limit      새 기능
fix/payment-timeout      버그 수정
refactor/order-service   구조 개선
docs/api-guide           문서 변경
chore/update-dependency  설정·의존성 작업
```

접두사는 팀마다 다를 수 있다. 중요한 것은 모든 팀원이 같은 규칙을 일관되게 사용하는 것이다.

## 4. Working Tree와 `git worktree`는 다르다

Git 문서에서 소문자 working tree는 현재 체크아웃된 파일이 놓인 작업 디렉터리를 뜻한다. 반면 `git worktree` 명령은 **하나의 저장소에 여러 작업 디렉터리를 연결하는 기능**이다.

일반적으로 한 디렉터리에서는 한 번에 하나의 브랜치만 체크아웃할 수 있다.

```bash
git switch feature/login
# 긴급 버그를 고치려면 작업을 정리한 뒤 다른 브랜치로 전환해야 한다.
git switch fix/payment
```

진행 중인 변경 때문에 브랜치를 바꾸기 어렵다면 `git stash`를 사용할 수도 있지만, 작업을 숨겼다가 다시 복원하는 과정이 필요하다. `git worktree`를 사용하면 브랜치별 디렉터리를 동시에 열 수 있다.

```bash
# 현재 저장소와 같은 상위 디렉터리에 새 워크트리 생성
git worktree add ../project-payment-fix -b fix/payment-timeout main
```

결과는 다음과 같다.

```text
project/                 → feature/login 브랜치
project-payment-fix/     → fix/payment-timeout 브랜치
```

두 디렉터리는 Working Tree와 Index를 각각 가지지만 `.git`의 객체와 커밋 이력은 공유한다. 저장소 전체를 다시 clone하는 것보다 공간을 적게 사용하며, 브랜치 전환 없이 두 작업을 동시에 실행할 수 있다.

### 워크트리 확인과 제거

```bash
git worktree list
git worktree remove ../project-payment-fix
git worktree prune
```

`remove`는 워크트리 디렉터리에 커밋하지 않은 변경이 있으면 기본적으로 거부된다. 변경을 확인하고 커밋하거나 안전하게 보관한 뒤 제거해야 한다. `prune`은 이미 사라진 워크트리의 관리 정보만 정리한다.

### 워크트리를 사용할 때 주의할 점

- 같은 브랜치를 여러 워크트리에 동시에 체크아웃할 수 없다.
- 워크트리마다 의존성 설치와 환경 설정 파일이 필요할 수 있다.
- 같은 포트를 사용하는 서버를 동시에 실행하면 충돌한다.
- 한 워크트리에서 만든 커밋과 브랜치는 다른 워크트리에서도 바로 보인다.
- 디렉터리를 파일 탐색기에서 바로 삭제하기보다 `git worktree remove`를 사용한다.

워크트리는 여러 기능을 무작정 동시에 개발하기 위한 도구라기보다, 긴 작업을 유지하면서 긴급 수정이나 코드 리뷰를 별도 환경에서 처리할 때 특히 유용하다.

## 5. 팀에서 사용하는 기본 브랜치 흐름

팀마다 Git Flow, GitHub Flow, trunk-based development 등 다양한 전략을 사용한다. 학생 프로젝트나 소규모 웹 서비스에서는 짧게 유지되는 기능 브랜치와 Pull Request를 사용하는 GitHub Flow 방식이 이해하기 쉽다.

```text
Issue 생성
   ↓
main에서 기능 브랜치 생성
   ↓
코드 작성과 작은 커밋
   ↓
원격 브랜치로 push
   ↓
Pull Request 생성
   ↓
자동 테스트와 코드 리뷰
   ↓
main에 merge
   ↓
기능 브랜치 삭제
```

### 1단계: 작업 범위 정하기

코드를 수정하기 전에 Issue나 작업 카드에 목적과 완료 조건을 적는다.

```text
목적: 로그인 실패 5회 이후 10분 동안 로그인을 제한한다.
완료 조건:
- 실패 횟수가 저장된다.
- 5회 실패 후 로그인 요청이 거절된다.
- 10분 후 다시 시도할 수 있다.
- 단위 테스트가 추가된다.
```

범위가 분명하면 브랜치와 PR이 작아지고 리뷰하기 쉬워진다.

### 2단계: 최신 main에서 브랜치 만들기

```bash
git switch main
git pull --ff-only
git switch -c feature/login-attempt-limit
```

오래된 `main`에서 시작하면 이미 바뀐 코드 위에 작업하게 되어 나중에 충돌할 가능성이 커진다.

### 3단계: 논리적인 단위로 커밋하기

```bash
git add src/domain/LoginAttempt.ts
git commit -m "로그인 실패 횟수 모델 추가"

git add src/service/AuthService.ts tests/AuthService.test.ts
git commit -m "로그인 시도 제한 적용"
```

한 커밋에는 한 가지 목적의 변경만 넣는 것이 좋다. 기능 추가와 무관한 대규모 포맷 변경을 함께 넣으면 실제 로직을 검토하기 어렵다.

### 4단계: PR 전 스스로 검증하기

```bash
git status
git diff main...HEAD
npm test
npm run build
```

`git diff main...HEAD`는 공통 조상 이후 내 브랜치에 추가된 변경을 보여준다. 불필요한 디버깅 코드, 비밀 값, 생성 파일이 포함되지 않았는지 확인한다.

### 5단계: push하고 PR 만들기

```bash
git push -u origin feature/login-attempt-limit
```

GitHub에서 base 브랜치는 변경이 들어갈 `main`, compare 브랜치는 내 기능 브랜치로 선택한다.

## 6. Pull Request는 무엇인가

Pull Request(PR)는 “내 브랜치의 변경을 대상 브랜치에 반영해 달라”는 요청이다. 코드를 합치는 버튼만이 아니라 다음 정보를 공유하는 협업 공간이다.

- 왜 이 변경이 필요한가?
- 무엇을 어떻게 바꿨는가?
- 어떤 방법으로 검증했는가?
- 리뷰어가 특히 확인해야 할 부분은 어디인가?
- 배포나 데이터베이스 변경 시 주의점은 무엇인가?

좋은 PR은 코드를 처음 보는 사람도 변경의 맥락과 위험을 파악할 수 있게 한다.

### PR 제목 예시

```text
feat: 로그인 실패 횟수 제한 추가
fix: 결제 요청 timeout 시 중복 승인 방지
refactor: 주문 가격 계산을 도메인 객체로 이동
docs: 로컬 실행 방법 추가
```

제목은 구현 방법보다 사용자가 체감할 변경이나 해결한 문제를 드러내는 편이 좋다.

### PR 본문 예시

```markdown
## 변경 배경

무제한 로그인 시도로 계정 보안 위험이 있었습니다.

## 변경 내용

- 사용자별 로그인 실패 횟수를 기록합니다.
- 5회 실패하면 10분 동안 로그인을 제한합니다.
- 로그인 성공 시 실패 횟수를 초기화합니다.

## 검증

- AuthService 단위 테스트 통과
- 제한 시간 전·후 로그인 시나리오 수동 확인

## 리뷰 포인트

- 여러 서버에서 동시에 요청할 때 실패 횟수가 정확히 증가하는지 확인 부탁드립니다.
```

화면이 바뀌었다면 스크린샷이나 영상을, API가 바뀌었다면 요청·응답 예시를 추가한다. DB Schema, 환경 변수, 배포 순서가 달라진다면 반드시 명시해야 한다.

## 7. 팀에서 정하면 좋은 PR 규칙

정답인 규칙은 없지만 다음 항목을 미리 합의하면 협업 과정의 오해를 줄일 수 있다.

### PR은 작게 유지한다

하나의 PR은 하나의 목적만 다룬다. 변경 줄 수에 절대적인 기준은 없지만 리뷰어가 전체 맥락을 한 번에 이해하기 어렵다면 분리해야 한다.

큰 기능은 다음처럼 나눌 수 있다.

1. 데이터 모델과 마이그레이션
2. 서버 API와 테스트
3. 화면 연결
4. 기존 코드 정리

단, 중간 PR이 시스템을 깨뜨리지 않도록 기능 플래그나 하위 호환성을 고려한다.

### 작성자가 먼저 Self Review한다

PR을 만든 직후 Files changed 화면을 직접 읽는다. 오타, 임시 로그, 주석 처리된 코드, 테스트 누락은 리뷰 요청 전에 정리한다. 작성자가 5분 확인하면 리뷰어 여러 명의 시간을 아낄 수 있다.

### 자동 검사를 통과해야 병합한다

일반적으로 다음 검사를 CI에서 실행한다.

- compile 또는 type check
- unit·integration test
- lint와 formatting
- build
- 의존성 및 보안 검사

브랜치 보호 규칙을 설정해 검사가 실패한 PR이나 필요한 승인 수를 채우지 못한 PR은 `main`에 병합하지 못하게 할 수 있다.

### 최소 한 명 이상의 승인을 받는다

작성자가 자신의 PR을 바로 병합하지 않고 다른 팀원의 승인을 받도록 한다. 결제, 인증, 개인정보처럼 위험이 큰 코드는 해당 영역 담당자의 승인을 요구할 수 있다.

리뷰 의견의 심각도도 구분하면 의사소통이 쉬워진다.

```text
[blocker] 병합 전에 반드시 수정해야 합니다.
[suggestion] 더 나은 방법을 제안하지만 필수는 아닙니다.
[question] 의도를 이해하기 위한 질문입니다.
[nit] 사소한 표현이나 스타일 의견입니다.
```

### 모든 대화가 해결된 뒤 병합한다

코드를 고쳤다면 “수정했습니다”만 남기기보다 어떤 방식으로 바꿨는지 답한다. 의견을 반영하지 않았다면 기술적인 이유를 설명하고 합의한다. 미해결 대화를 남긴 채 병합하지 않는다.

### main에 직접 push하지 않는다

공용 `main`은 항상 빌드·배포 가능한 상태를 유지한다. 긴급 수정도 별도의 브랜치와 PR을 거치는 것이 원칙이다. 정말 예외가 필요하다면 누가 어떤 상황에서 직접 수정할 수 있는지 팀 규칙에 명시한다.

## 8. Merge, Squash, Rebase 중 무엇을 쓸까

GitHub에서 PR을 병합할 때 대표적으로 세 가지 방식을 선택할 수 있다.

| 방식 | 결과 | 적합한 상황 |
| --- | --- | --- |
| Merge commit | 브랜치의 커밋과 병합 지점을 모두 보존 | 브랜치 단위 흐름을 남기고 싶을 때 |
| Squash and merge | PR의 여러 커밋을 하나로 합침 | 기능 단위로 단순한 main 이력을 원할 때 |
| Rebase and merge | 커밋을 main 위에 일렬로 재배치 | 개별 커밋도 깔끔하게 관리할 때 |

학생 프로젝트나 작은 팀에서는 **Squash and merge**가 관리하기 쉽다. 기능 브랜치에서 “오타 수정”, “리뷰 반영” 같은 중간 커밋이 많아도 `main`에는 PR 하나가 커밋 하나로 남는다.

어떤 방식을 택하든 팀 전체가 하나로 통일하는 편이 좋다. Rebase는 이미 다른 사람이 기반으로 작업 중인 공유 브랜치의 이력을 강제로 바꾸지 않도록 주의해야 한다.

## 9. 최신 main 반영과 충돌 해결

PR을 검토하는 동안 `main`이 변경되면 내 브랜치에도 최신 변경을 반영해야 할 수 있다.

### Merge 방식

```bash
git fetch origin
git merge origin/main
```

기존 커밋을 바꾸지 않아 안전하지만 기능 브랜치에 merge commit이 생긴다.

### Rebase 방식

```bash
git fetch origin
git rebase origin/main
```

내 커밋을 최신 `main` 위에 다시 적용해 이력을 일렬로 만든다. 이미 원격에 올린 브랜치를 rebase했다면 일반 push가 거부될 수 있다.

```bash
git push --force-with-lease
```

`--force-with-lease`는 다른 사람이 원격 브랜치에 추가한 커밋이 있으면 덮어쓰지 않고 실패한다. 단순한 `--force`보다 안전하지만, 공유 브랜치에서는 팀과 합의한 경우에만 사용한다.

### 충돌이 발생했을 때

```text
<<<<<<< HEAD
현재 브랜치의 코드
=======
합치려는 브랜치의 코드
>>>>>>> origin/main
```

충돌 표시는 둘 중 하나를 무조건 선택하라는 뜻이 아니다. 양쪽 변경의 의도를 이해한 뒤 최종 코드가 어떻게 되어야 하는지 직접 결정해야 한다.

```bash
# 충돌 파일 수정 후
git add src/AuthService.ts

# merge 중이었다면
git commit

# rebase 중이었다면
git rebase --continue
```

충돌 해결 후에는 반드시 테스트를 다시 실행한다. 문법상 충돌이 해결돼도 두 기능의 동작이 논리적으로 충돌할 수 있다.

## 10. 리뷰어는 무엇을 확인해야 할까

코드 리뷰는 작성자를 평가하는 과정이 아니라 결함과 지식을 팀 전체가 나누는 과정이다. 리뷰어는 코드 스타일만 보기보다 다음 순서로 확인하는 것이 좋다.

1. PR의 목적과 요구사항이 명확한가?
2. 구현이 요구사항을 실제로 만족하는가?
3. 더 단순한 설계로 해결할 수 있는가?
4. 예외, 경계값, 동시성, 보안 문제가 있는가?
5. 테스트가 중요한 동작과 실패 상황을 검증하는가?
6. 기존 API와 데이터에 미치는 영향이 설명됐는가?
7. 운영 중 문제를 관찰하고 되돌릴 수 있는가?

리뷰 의견은 코드가 아니라 근거와 영향을 중심으로 작성한다.

```text
나쁜 예: 이 코드는 이상해요.

좋은 예: 두 요청이 동시에 실행되면 마지막 저장이 앞선 값을 덮어써
실패 횟수가 누락될 수 있습니다. DB의 원자적 증가 연산을 사용하는 것은 어떨까요?
```

## 11. 실제 협업 예시

두 명이 쇼핑몰 프로젝트를 개발한다고 가정하자.

- 민수: 장바구니 쿠폰 기능 개발
- 지수: 운영 중 발견된 결제 timeout 버그 수정

민수는 기존 디렉터리에서 기능 브랜치를 작업 중이다.

```bash
git switch -c feature/cart-coupon
```

긴급 버그를 함께 확인해야 하지만 아직 커밋하지 않은 변경이 있다. 이때 별도 워크트리를 만든다.

```bash
git fetch origin
git worktree add ../shop-payment-fix -b fix/payment-timeout origin/main
```

지수와 결제 수정 작업을 마친 뒤 다음 과정을 거친다.

```bash
cd ../shop-payment-fix
git add src/payment tests/payment
git commit -m "결제 timeout 재시도 시 중복 승인 방지"
git push -u origin fix/payment-timeout
```

PR에는 재현 방법, 원인, 수정 방식, 테스트 결과를 기록한다. CI 통과와 리뷰 승인을 확인한 뒤 `main`에 squash merge한다. 이후 워크트리를 제거한다.

```bash
cd ../shop
git worktree remove ../shop-payment-fix
git branch -d fix/payment-timeout
```

민수의 원래 작업 디렉터리와 변경은 그대로 남아 있으므로 쿠폰 기능을 이어서 개발할 수 있다.

## 12. 팀 규칙 예시

처음 협업하는 팀이라면 다음 정도의 규칙으로 시작할 수 있다.

```text
1. main에는 직접 push하지 않는다.
2. 모든 변경은 Issue와 기능 브랜치에서 시작한다.
3. 하나의 PR은 하나의 목적만 다룬다.
4. PR 작성자는 리뷰 요청 전 Self Review와 테스트를 수행한다.
5. CI 통과와 팀원 1명 이상의 승인을 병합 조건으로 한다.
6. 미해결 리뷰가 있으면 병합하지 않는다.
7. PR은 Squash and merge하고 병합 후 브랜치를 삭제한다.
8. DB·API·환경 변수 변경은 PR 본문에 명시한다.
9. 긴급 수정에도 가능한 한 동일한 PR 절차를 적용한다.
```

팀이 성장하면 코드 소유자, 승인 인원, 릴리스 브랜치, 배포 승인 같은 규칙을 추가할 수 있다. 처음부터 복잡한 규칙을 모두 도입하기보다 실제로 반복되는 문제를 해결하는 방향으로 발전시키는 것이 좋다.

## 마무리

브랜치는 독립적인 파일 복사본이 아니라 커밋을 가리키는 포인터이고, Working Tree는 그 커밋을 실제 파일로 펼쳐 작업하는 공간이다. `git worktree`는 하나의 저장소에 여러 Working Tree를 연결해 서로 다른 브랜치를 동시에 다룰 수 있게 한다.

Pull Request의 목적은 단순히 코드를 합치는 것이 아니다. 변경의 이유를 설명하고, 자동 검사와 동료 리뷰를 통해 위험을 줄이며, 팀이 코드와 설계 지식을 공유하는 과정이다.

좋은 Git 협업은 명령어를 많이 아는 것보다 **작은 작업 단위, 명확한 커밋, 설명 가능한 PR, 일관된 팀 규칙**에서 시작한다.
