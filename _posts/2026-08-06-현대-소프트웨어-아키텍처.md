앞선 글에서는 모놀리스의 성장 과정과 MSA의 등장 배경을 살펴봤다. 서비스를 나누는 것만으로 좋은 시스템이 완성되지는 않는다. 서비스 내부에서 비즈니스 규칙이 프레임워크에 종속될 수 있고, 서비스 사이의 데이터 일관성이 깨질 수 있으며, 늘어난 배포 단위를 사람이 감당하지 못할 수도 있다.

현대 소프트웨어 아키텍처의 여러 패턴과 운영 기술은 이런 문제를 서로 다른 관점에서 해결한다.

- Clean·Hexagonal Architecture: 핵심 로직과 외부 기술의 의존성 문제
- CQRS: 읽기와 쓰기의 요구가 다른 문제
- Event Driven Architecture: 서비스 간 결합과 비동기 처리 문제
- Saga: 여러 서비스에 걸친 데이터 일관성 문제
- Docker·Kubernetes·CI/CD: 반복 가능한 배포와 운영 문제

모든 패턴을 한 시스템에 적용할 필요는 없다. 각 패턴이 해결하려는 문제가 실제로 존재하는지 먼저 확인해야 한다.

## 1. Clean Architecture: 의존성의 방향을 바꾸다

전통적인 계층형 구조에서는 흔히 다음과 같은 의존 관계가 만들어진다.

```text
Controller → Service → Repository → Database
```

흐름 자체는 자연스럽지만 Service가 ORM Entity, SQL, 웹 프레임워크에 직접 의존하면 비즈니스 규칙을 기술과 분리해 테스트하거나 교체하기 어렵다.

Clean Architecture는 로버트 C. 마틴이 대중화한 구조로, 핵심 정책을 중심에 두고 외부 기술을 바깥에 배치한다. 가장 중요한 규칙은 **소스 코드의 의존성이 안쪽을 향해야 한다**는 것이다.

```text
┌────────────────────────────────────┐
│ Frameworks & Drivers               │
│  ┌──────────────────────────────┐  │
│  │ Interface Adapters           │  │
│  │  ┌────────────────────────┐  │  │
│  │  │ Application Use Cases  │  │  │
│  │  │  ┌──────────────────┐  │  │  │
│  │  │  │ Domain Entities  │  │  │  │
│  │  │  └──────────────────┘  │  │  │
│  │  └────────────────────────┘  │  │
│  └──────────────────────────────┘  │
└────────────────────────────────────┘
              의존성 → 안쪽
```

주문 저장 기능을 예로 들면 Application 계층은 구체적인 JPA Repository 대신 자신에게 필요한 인터페이스를 정의한다.

```java
// application/port/OrderStore.java
public interface OrderStore {
    Order save(Order order);
}

// application/usecase/CreateOrder.java
public class CreateOrder {
    private final OrderStore orderStore;

    public OrderId execute(CreateOrderCommand command) {
        Order order = Order.create(command.customerId(), command.items());
        return orderStore.save(order).getId();
    }
}

// adapter/persistence/JpaOrderAdapter.java
public class JpaOrderAdapter implements OrderStore {
    private final SpringDataOrderRepository repository;

    @Override
    public Order save(Order order) {
        return repository.save(OrderJpaEntity.from(order)).toDomain();
    }
}
```

비즈니스 규칙은 JPA를 모르며, 바깥쪽 Adapter가 안쪽의 인터페이스를 구현한다. 이를 의존성 역전이라고 한다. 데이터베이스를 바꾸지 않더라도 테스트에서 메모리 구현을 주입할 수 있다는 장점이 있다.

다만 단순한 CRUD 서비스에 계층과 변환 코드를 과도하게 추가하면 이해 비용만 늘 수 있다. 복잡하고 오래 유지되는 핵심 도메인에서 효과가 크다.

## 2. Hexagonal Architecture: Port와 Adapter

알리스테어 코번이 제안한 Hexagonal Architecture는 애플리케이션을 외부 세계와 분리한다. 육각형 모양 자체가 중요한 것은 아니다. 애플리케이션과 외부 기술의 경계를 **Port**라는 계약으로 만들고, 구체적인 연결을 **Adapter**가 담당한다는 점이 핵심이다.

```text
                   REST Controller
                         │
                  Inbound Adapter
                         │
                         ▼
                [ CreateOrder Port ]
                [   Application     ]
                [    OrderStore     ]
                    │           │
          Outbound Adapter   Outbound Adapter
                    │           │
                   JPA      Payment API
```

- Inbound Port: 외부에서 애플리케이션을 호출하는 유스케이스 계약
- Inbound Adapter: REST Controller, CLI, 메시지 소비자
- Outbound Port: 애플리케이션이 외부 기능을 사용하기 위한 계약
- Outbound Adapter: 데이터베이스, 외부 API, 메시지 생산자

Clean Architecture와 Hexagonal Architecture는 용어와 도식은 다르지만 핵심 목표가 비슷하다. 도메인과 유스케이스를 중심에 두고 프레임워크와 입출력 기술을 교체 가능한 바깥 요소로 다룬다.

## 3. CQRS: 명령과 조회를 분리하기

일반적인 CRUD 모델은 같은 객체와 저장소로 데이터를 쓰고 읽는다. 작은 시스템에서는 가장 단순한 선택이다. 그러나 쓰기와 읽기의 요구가 크게 달라질 수 있다.

- 쓰기: 주문 규칙 검증, 재고 확인, 트랜잭션과 일관성이 중요하다.
- 읽기: 주문·상품·배송 정보를 한 화면에 빠르게 보여줘야 한다.

CQRS(Command Query Responsibility Segregation)는 상태를 변경하는 Command와 데이터를 반환하는 Query의 모델을 분리한다.

```text
Command API → Write Model → Orders DB
                              │ event
                              ▼
Query API   ← Read Model  ← Order View DB
```

처음부터 데이터베이스를 두 개로 나눌 필요는 없다. 코드 수준에서 명령과 조회 책임을 나누는 것부터 시작할 수 있다.

```java
// 상태를 변경하고 결과 ID만 반환한다.
OrderId handle(CreateOrderCommand command);

// 상태를 변경하지 않고 화면에 필요한 데이터를 반환한다.
OrderDetailView handle(GetOrderDetailQuery query);
```

트래픽과 조회 복잡도가 커지면 쓰기 DB와 읽기 DB를 분리하고 이벤트로 읽기 모델을 갱신할 수 있다. 읽기 모델은 화면에 맞게 여러 데이터를 미리 결합해 둘 수 있어 빠르다. 반면 이벤트가 전달되어 반영되기 전까지 최신 쓰기 결과가 조회되지 않는 **최종적 일관성**이 발생한다.

CQRS는 복잡한 도메인, 쓰기와 읽기의 부하 차이가 큰 시스템, 다양한 조회 화면에서 유용하다. 단순 CRUD에서는 모델과 동기화 지점만 늘릴 수 있다.

## 4. Event Driven Architecture

Event Driven Architecture(EDA)는 시스템에서 발생한 상태 변화를 이벤트로 표현하고, 다른 구성 요소가 이를 구독해 반응하는 구조다.

주문 서비스가 알림 서비스를 직접 호출하면 두 서비스가 시간적으로 결합된다.

```text
주문 서비스 → 알림 서비스 호출 → 응답을 기다림
```

이벤트를 사용하면 주문 서비스는 주문이 생성됐다는 사실만 발행한다.

```text
주문 서비스 → OrderCreated → Message Broker
                                  ├─→ 알림 서비스
                                  ├─→ 분석 서비스
                                  └─→ 배송 서비스
```

### Event와 Command의 차이

- Command는 “재고를 예약하라”처럼 수행하기 원하는 일을 표현한다.
- Event는 “주문이 생성됐다”처럼 이미 발생한 사실을 과거형으로 표현한다.

이벤트 생산자는 누가 소비하는지 알 필요가 없으므로 새 소비자를 추가하기 쉽다. 메시지 브로커가 순간적인 트래픽을 흡수하고 소비자가 복구된 뒤 다시 처리할 수도 있다.

### 신뢰할 수 있는 이벤트 발행: Transactional Outbox

데이터베이스 저장과 메시지 발행을 순서대로 실행하면 둘 중 하나만 성공할 수 있다.

```text
1. 주문 DB 저장 성공
2. 메시지 발행 실패  ← 주문은 있지만 이벤트는 없음
```

Transactional Outbox 패턴은 주문 데이터와 발행할 이벤트를 같은 DB 트랜잭션에 저장한다. 별도 Publisher가 Outbox를 읽어 브로커에 전달한다.

```sql
BEGIN;
INSERT INTO orders(id, status) VALUES ('order-100', 'CREATED');
INSERT INTO outbox(event_id, event_type, payload)
VALUES ('evt-1', 'OrderCreated', '{...}');
COMMIT;
```

브로커나 Publisher의 재시도로 이벤트가 중복 전달될 수 있으므로 소비자는 이미 처리한 `eventId`를 기록하거나 같은 이벤트를 여러 번 처리해도 결과가 같도록 멱등하게 구현해야 한다.

## 5. Saga: 분산된 작업의 일관성 유지

하나의 데이터베이스에서는 ACID 트랜잭션으로 여러 변경을 원자적으로 처리할 수 있다. 그러나 주문, 재고, 결제가 각각 자신의 DB를 가진다면 하나의 로컬 트랜잭션으로 묶을 수 없다.

Saga 패턴은 긴 비즈니스 트랜잭션을 여러 서비스의 로컬 트랜잭션으로 나누고, 중간에 실패하면 이미 완료된 작업을 **보상 트랜잭션**으로 취소한다.

```text
주문 생성 → 재고 예약 → 결제 승인 → 주문 확정
               성공        실패
                └──── 재고 예약 취소 ← 주문 취소
```

보상은 데이터베이스 rollback과 다르다. 이미 실행된 일을 의미상 되돌리는 별도의 업무 동작이다. 카드 결제 취소가 즉시 승인 이전 상태로 돌아가는 것이 아니라 환불 내역을 새로 만드는 것과 같다.

### Choreography 방식

각 서비스가 이벤트를 구독하고 다음 이벤트를 발행한다.

```text
OrderCreated → StockReserved → PaymentApproved → OrderConfirmed
```

중앙 제어자가 없어 서비스 결합이 낮지만 흐름이 길어지면 전체 과정을 파악하기 어렵다.

### Orchestration 방식

Saga Orchestrator가 각 서비스에 명령을 보내고 결과에 따라 다음 단계나 보상을 결정한다.

```java
switch (saga.state()) {
    case ORDER_CREATED -> reserveStock(saga.orderId());
    case STOCK_RESERVED -> requestPayment(saga.orderId());
    case PAYMENT_FAILED -> cancelStockReservation(saga.orderId());
}
```

흐름과 상태를 한곳에서 관찰하기 쉽지만 Orchestrator가 업무 흐름을 많이 알게 된다. 어느 방식을 사용하든 timeout, 중복 메시지, 순서 역전, 수동 복구 절차까지 설계해야 한다.

## 6. DevOps: 개발과 운영을 하나의 흐름으로

DevOps는 특정 도구 하나가 아니라 개발과 운영 사이의 장벽을 줄이고, 소프트웨어를 작고 빈번하게 안전하게 전달하기 위한 문화와 실천 방식이다. MSA에서는 서비스 수가 늘어나므로 자동화가 선택이 아니라 운영 조건에 가까워진다.

### Docker: 동일한 실행 단위

Docker는 애플리케이션과 실행 환경을 이미지로 패키징한다. 이미지 태그나 digest를 기준으로 어떤 버전이 배포됐는지 추적하고 같은 결과물을 여러 환경에서 실행할 수 있다.

### Kubernetes: 원하는 상태 유지

Kubernetes에서는 “컨테이너를 실행하라”보다 “이 애플리케이션 Pod가 항상 3개 존재해야 한다”처럼 원하는 상태를 선언한다. 컨트롤러가 실제 상태를 관찰하고 차이를 조정한다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: order-service
  template:
    metadata:
      labels:
        app: order-service
    spec:
      containers:
        - name: order-service
          image: example/order-service:1.2.0
          ports:
            - containerPort: 8080
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
```

Readiness Probe가 실패한 Pod에는 트래픽을 보내지 않는다. 다만 Kubernetes를 사용한다고 애플리케이션이 자동으로 분산 시스템에 안전해지는 것은 아니다. 상태 관리, 종료 처리, 리소스 제한과 관측성은 애플리케이션에서도 설계해야 한다.

### CI/CD: 변경을 검증하고 전달하는 파이프라인

CI(Continuous Integration)는 작은 변경을 자주 통합하며 자동으로 빌드와 테스트를 수행하는 실천이다. CD는 검증된 결과물을 운영 환경까지 전달하거나 배포할 수 있는 상태로 유지한다.

```text
Commit
  → Compile
  → Unit Test
  → Integration Test
  → Image Build & Security Scan
  → Staging Deploy
  → Smoke Test
  → Production Deploy
```

배포 후에는 로그만으로 충분하지 않다. 메트릭, 구조화된 로그, 분산 추적, 알림을 함께 구축해야 여러 서비스에 걸친 요청의 지연과 실패 지점을 찾을 수 있다. 아키텍처는 배포에서 끝나는 설계가 아니라 관찰하고 복구하는 방식까지 포함한다.

## 7. 현재의 흐름: 다시 경계를 가진 모놀리스로

MSA가 널리 알려진 뒤, 필요보다 일찍 서비스를 분리해 운영 복잡성만 커진 사례도 많아졌다. 그 결과 최근에는 **Modular Monolith**와 **Monolith First**가 현실적인 출발점으로 다시 주목받고 있다.

### Modular Monolith

Modular Monolith는 하나의 프로세스로 배포하지만 내부 모듈의 경계와 의존 규칙을 명확히 유지한다.

```text
하나의 배포 단위
┌──────────────────────────────────┐
│ Order Module                     │
│   공개 API: OrderFacade          │
│   내부 구현: 외부 접근 불가       │
├──────────────────────────────────┤
│ Payment Module                   │
│   공개 API: PaymentFacade        │
│   내부 구현: 외부 접근 불가       │
└──────────────────────────────────┘
```

모듈은 다른 모듈의 내부 클래스나 테이블을 직접 사용하지 않고 공개 API나 내부 이벤트로 통신한다. Java에서는 멀티 모듈 빌드와 패키지 접근 제한을, 다른 언어에서도 모듈 시스템이나 정적 분석을 사용해 규칙을 검사할 수 있다.

장점은 모놀리스의 단순한 배포와 트랜잭션을 유지하면서 경계를 학습할 수 있다는 점이다. 나중에 독립 배포가 필요한 모듈이 분명해지면 그 경계를 기준으로 서비스를 추출할 수 있다.

### Monolith First

Monolith First는 시스템 초기에는 모놀리스로 도메인과 제품을 학습하고, 충분한 근거가 생겼을 때 분리한다는 전략이다. 초기에는 업무 경계를 정확히 알기 어렵다. 섣불리 서비스를 나누면 잘못된 경계가 API와 네트워크 계약으로 굳어져 오히려 수정하기 어렵다.

다만 “나중에 분리하자”는 말만으로 경계가 생기지는 않는다. 처음부터 모듈 소유권, 의존 방향, 데이터 접근 규칙을 지키고 테스트해야 한다.

## 8. 언제 MSA를 선택해야 할까

다음 조건이 실제로 나타날 때 MSA의 이점이 비용을 넘어설 가능성이 크다.

- 서로 다른 기능이 독립적인 주기로 자주 배포돼야 한다.
- 특정 기능만 트래픽 특성이 크게 달라 독립 확장이 필요하다.
- 여러 팀이 명확한 도메인 경계를 기준으로 자율적으로 일한다.
- 장애를 서비스 단위로 격리해야 할 강한 요구가 있다.
- 자동 배포, 모니터링, 장애 대응을 운영할 역량이 있다.

반대로 다음 상황이라면 잘 설계된 모놀리스가 더 적합할 수 있다.

- 제품과 도메인이 아직 자주 바뀐다.
- 팀 규모가 작고 배포 주기가 비슷하다.
- 강한 트랜잭션 일관성이 핵심이다.
- 트래픽이 단일 애플리케이션으로 충분히 처리된다.
- 분산 시스템 운영 경험과 자동화 기반이 부족하다.

아키텍처 선택은 애플리케이션 크기만으로 결정되지 않는다. **독립적으로 변경할 필요**, **조직 구조**, **운영 역량**을 함께 봐야 한다.

## 9. 학생 프로젝트에 적용해 본다면

학부 프로젝트에서 처음부터 Kubernetes와 수십 개의 마이크로서비스를 구성하는 것은 학습 목표가 아니라면 과도할 수 있다. 다음 순서로 발전시키면 각 단계의 이유를 직접 경험할 수 있다.

1. 하나의 애플리케이션으로 핵심 유스케이스를 완성한다.
2. Controller, Application, Domain, Infrastructure의 책임을 분리한다.
3. 주문·결제·회원처럼 업무 모듈의 공개 API와 데이터 소유권을 정한다.
4. 통합 테스트와 CI를 구성한다.
5. 실제로 독립 배포나 확장이 필요한 모듈 하나만 서비스로 분리한다.
6. timeout, retry, 멱등성, 로그 추적 등 분산 시스템 문제를 관찰한다.

이 과정에서 “어떤 기술을 사용했다”보다 “어떤 문제 때문에 이 경계를 선택했고, 무엇을 포기했는가”를 설계 문서에 남기는 것이 중요하다. 이런 기록을 ADR(Architecture Decision Record)로 관리할 수 있다.

```markdown
# ADR-003: 주문과 결제를 비동기 이벤트로 연결

- 배경: 결제 지연이 주문 API의 응답 시간을 증가시킴
- 결정: OrderCreated 이벤트를 발행하고 결제 서비스가 처리
- 결과: 응답 결합은 줄지만 최종적 일관성과 중복 처리가 필요함
```

## 마무리

현대 아키텍처 패턴은 유행하는 기술 목록이 아니라 반복해서 나타난 문제에 대한 선택지다. Clean·Hexagonal Architecture는 핵심 정책을 외부 기술로부터 보호한다. CQRS는 읽기와 쓰기의 서로 다른 요구를 분리한다. EDA와 Saga는 분산된 서비스의 통신과 일관성을 다룬다. Docker, Kubernetes, CI/CD는 이 구조를 반복 가능하게 배포하고 운영하도록 돕는다.

그러나 패턴을 적용할수록 코드, 인프라, 운영의 복잡성도 증가한다. 좋은 아키텍처는 미래의 모든 가능성을 미리 구현하는 구조가 아니라, 현재의 문제를 해결하면서 다음 변경을 감당할 여지를 남기는 구조다.
